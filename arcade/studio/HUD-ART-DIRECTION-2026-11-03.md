# «Выживший» — художественная система HUD, версия Art Pass 01

Дата: 3 ноября 2026 года. Источник художественного направления — приложенный пользователем референс 1536×864. Реализован отдельный испытательный стенд: `arcade/studio/hud-preview.html`. **Это ещё не действующий HUD игры.**

## Что именно берём из референса

- Информационные блоки разнесены по краям. У игрока остаётся свободная центральная часть экрана.
- Рамки — тонкие металлические контуры со скосами, внутри почти прозрачное затемнённое стекло.
- Цвета несут устойчивые значения: холодный голубой — система и шкалы, янтарный — готовность/особое действие, красный — угроза.
- Пиктограммы и сегменты шкал имеют собственную геометрию. Не подменять их шрифтовыми emoji или обычными прямоугольными карточками.
- Задача — вытянутая верхняя лента с отдельным расстоянием. Ближний радар — самостоятельный круглый прибор справа.
- Взаимодействие с миром маркируется около объекта с короткой подписью и направляющей; предупреждения о попаданиях — ближе к кораблю.
- Приборные рамки и графические знаки остаются неизменными; меняются только реальные числа, длина шкал, доступность навыков и сигналы событий.

## Устройство графики

Для браузерного Canvas 2D не требуется переходить на Phaser, Godot или WebGL. Сейчас основная игра уже разделяет игровой рендер, DOM-панели и локальный радар. Поэтому:

1. **Статические ресурсы SVG** загружаются один раз: `panel-left.svg`, `panel-right.svg`, `mission-ribbon.svg`, `ability-frame.svg`, `radar-bezel.svg`, `ship-outline.svg`, `weapon.svg`, `drone.svg`, три пиктограммы действия и три варианта сегментированной шкалы. Все SVG лежат в `arcade/studio/hud-kit/`.
2. **Динамические слои** — текст DOM и заполнение сегментов с отсечением готового SVG-рисунка. CSS нужен для привязки к краям и масштабирования, а не для рисования художественной формы приборов.
3. **Радар** остаётся Canvas 2D с ограниченным радиусом и обновлением не чаще 5 раз в секунду. Декоративный ободок — самостоятельный SVG поверх него.
4. **Сигналы в игровом мире** рисуются в координатах камеры: маркер взаимодействия, дуга направления удара, выделение цели. Их нужно подключать к уже существующим событиям, не создавать вторую систему поиска целей.
5. **Анимации** локальны: краткая вспышка при получении ресурса, появление задачи, единичный импульс урона. Нет постоянной вибрации всего HUD, размытия всей сцены и тяжёлых теней на десятках контактов.
6. **Масштабирование**: размер готовой панели меняется в допустимых пределах. Если ширина существенно меняется, позднее стоит разрезать её на углы, края и центральную часть (9-slice), чтобы скосы не деформировались. В первом макете панели сохраняют соотношение сторон.

## Сопоставление с действующими механиками

| Референс | В нашей игре | Решение |
| --- | --- | --- |
| Корпус, щит | `player.hp/maxHp`, `player.shield` | Настоящие значения; для щита уточнить верхний предел до вывода процентов |
| Энергия 86% | Общей шкалы энергии нет | Третью шкалу использовать для готовности рывка по `burstCooldown` / рассчитанному времени восстановления |
| Импульс 36/60 | Боезапаса пока нет | Показать состояние автоогня; числовой боезапас не вводить |
| Нагрев 62% | Перегрева пока нет | Круг может показывать реальный целочисленный запас авиаударов; не выводить ложные проценты нагрева |
| Дроны 2/3 | `allies` и реальный предел доступных ведомых | Рисовать столько действующих значков, сколько позволяет текущая механика, без фиксированных «трёх» |
| Три способности | Рывок, код, авиаудар, контекстные действия | Слоты появляются только по доступности; ремонт и добыча — действия удержанием, не постоянные кулдауны |
| Задача и расстояние | `missionHudText(game)`, позиция цели в мире при наличии | Текст реальной операции; дистанция только когда цель однозначно определена |
| Радар и маркеры | `radarPoint()`, станции, враги, союзники, зоны удара | Сохранить локальный диапазон и лимиты контактов |
| Повреждение вокруг корабля | События попадания и вектор урона | Привязать дугу к источнику удара; декоративный красный сектор без причины не показывать |

## Компоновки

**Компьютер и широкая альбомная область.** Почти буквальная композиция референса: верхняя задача, верхний радар, нижние левый и правый приборы, способности между ними.

**Телефон горизонтально.** Сенсорный джойстик и кнопки занимают нижние углы. Приборы смещаются выше, а крайние элементы уплотняются; центр сохраняется для корабля и цели.

**Телефон вертикально.** Слева вверху статус, справа радар; задача ниже, затем по очереди приборы корпуса и вооружения. Способности остаются над нижним сенсорным управлением. Это отдельная композиция, а не равномерно уменьшенный десктоп.

## Приёмка перед переносом в игру

- Сравнить макет с приложенным изображением при 1536×864: форма рамок, доля свободного пространства, иерархия, выразительность символов.
- Проверить 1366×768, 844×390, 390×844; нет наложений на сенсорные действия или выходов текста за контур.
- Проверить состояния «спокойный полёт», «бой» и «критическое повреждение» на стенде.
- В коде игры подключить реальные поля; отключённые механики нельзя изображать активными.
- Проверить один реальный цикл: подлёт к базе → действие → бой → повреждение → добыча → рывок → готовая награда.
- Выполнить тест на слабом телефоне с большим количеством противников; при снижении FPS не должен появляться дополнительный тяжёлый рендер.
- После просмотра стенда **попросить художественное согласование**. Только затем менять `arcade/hud.js`, `arcade/hud.css`, `arcade/index.html`.

## Граница готовности

Стенд и графические элементы — **первый художественный прототип**. Они уже позволяют проверить композицию, размеры и стиль, но ещё требуют визуального сравнения с оригиналом. Тестовые проценты и «УЗЕЛ 03» служат для демонстрации и не связаны с текущим игровым состоянием. Считать HUD внедрённым в игру пока нельзя.
